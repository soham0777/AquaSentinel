The first labelled row of each event is unperturbed (`sin(0) = 0`). Baseline model: sinusoidal diurnal cycles for temperature (±3.2 °C),

## 2. Decision algorithm (firmware `anomaly_engine.cpp`, Python `detector.py`)

### 2.1 Mathematics
For each 15-minute reading x of parameter p at local bin h:

* Hard limits: alarm if pH < 6 or > 9, DO < 4 mg/L, or EC > 2250 µS/cm (the last is CPCB **Class E**, not Class C).
* Baseline update (only while learning or when risk is NORMAL), α = 1/96:
  μ ← μ + α (x − μ);  d ← d + α (|x − μ_new| − d)
* Score: z = |x − μ| / max(1.4826·d, floor), floors pH 0.05, EC 10 µS/cm, DO 0.20 mg/L, turbidity 2 NTU. Outlier if z > 3.
* Persistence: EVENT when ≥ 2 of the last 3 readings have any outlier; WATCH for 1; back to NORMAL after 4 clean readings.
* Learning: the first 672 readings (7 days) only update baselines.

Notes on the maths:
* d is an EWMA of the **mean** absolute deviation. For Gaussian noise E|x − μ| = σ√(2/π) ≈ 0.80σ, so 1.4826·d ≈ 1.18σ and
  "z > 3" is ≈ 3.5σ. The constant 1.4826 belongs to the **median** absolute deviation.
* With α = 1/96 the EWMA memory is ≈ 96 updates. EC and turbidity (one bin, 96 updates/day) remember ≈ 1 day; each hourly pH/DO bin
  gets 4 updates a day, so its memory is ≈ 24 days. After 7 days of learning the hourly bins have moved only ≈ 25 % from their
  defaults (verified: DO bins 21–26 %).
* While μ is far from the truth, d inflates (|x − μ| is large), which *lowers* z. The practical effect after learning is reduced
  sensitivity for DO- and pH-driven events, not false alarms.
* Inputs not used: temperature (24 bins initialised, never scored), stage, rates of change (the "gradient" constants in the exported
  header are unused), relationships between parameters.

### 2.2 Training, fitting and configuration
No offline training. The state is learned online from cold-start defaults (pH 7.50 ± 0.15, DO 6.50 ± 0.40, EC 450 ± 35,
turbidity 12 ± 3). Thresholds (z 3, floors, 2-of-3, 4 clean cycles, 672 learning cycles) are hand-set; no tuning or sensitivity
study exists in the repository.

### 2.3 Evaluation as shipped
`evaluate.py` prints 2,808 NORMAL (97.5 %), 15 WATCH (0.5 %), 57 EVENT (2.0 %) and "25 Physical Forensic Samples Sealed". It does
not compare with the labels, so it cannot report latency, recall or false alarms although its docstring says it does. The README's
"4/4 within 30 minutes" is therefore not produced by any committed code.

### 2.4 Evaluation in this audit ([detector_event_metrics.py](../audit/verification/detector_event_metrics.py))
| Event | First EVENT | Latency from label start | Caught by | Sample triggers |
|---|---|---|---|---|
| Acid dump | row 490 | 30 min (15 min after the first perturbed row) | hard limit (pH) | 9 |
| Sewage overflow | row 1232 | 30 min | statistical | 11 |
| Salt spill | row 1966 | 30 min | statistical | 4 |
| Silt surge | row 2526 | 30 min | statistical | 1 |

* **Recall 4/4**; the README claim is confirmed on this dataset.
* **False alarms:** 3 EVENT cycles at rows 672–674 outside any event — not a statistical false positive but stale state: the acid-dump
  hard-limit trip set the risk to EVENT during the learning period and nothing reset it before learning ended (the firmware has the
  same flaw). No WATCH cycles outside events.
* **Sampling budget:** 25 triggers, because hard-limit trips trigger on every reading. With the firmware's 60-minute lockout and four
  bottles, bottles fill at rows 490, 494 and 498 (acid dump) and 1232 (sewage); the salt and silt events get no sample.
* **Firmware equivalence** ([firmware_engine_port.py](../audit/verification/firmware_engine_port.py), float32 port of the C++): levels and
  triggers identical on all 2,880 rows; flags differ on 8 rows and scores on 2,462, so "bit-for-bit" is an overstatement.
* **Robustness:** all probes failed (firmware fallback constants) → 0/4 detected; one brown-out reset on day 20 → salt spill detected
  45 minutes later (hard limit only) and silt surge missed.

### 2.5 Leakage and misleading metrics
* The detector is not trained on labels, so there is no label leakage in it. The evaluation, however, uses events far larger than the
  noise (above), so 4/4 is a weak result.
* `train_proxy_anomaly_engine.py` **uses the labels** to select the "normal" training rows and sets its threshold on the same rows
  (99.5th percentile) before reporting recall 87.5 % (56/64) and false-positive rate 0.53 %. Both numbers are in-sample; the FPR is
  fixed by construction. No hold-out data, no time split, no cross-validation. The resulting model is not used by the firmware.
* "Physical Forensic Samples Sealed: 25" contradicts the 4-bottle design.

### 2.6 Missing baselines, ablations, uncertainty and validation
* Baselines to compare against: fixed thresholds only; EWMA/CUSUM control charts per parameter; multivariate methods (the unused
  Mahalanobis model); EPA/Sandia **CANARY**, which was built for exactly this event-detection problem and has been used for
  watershed monitoring (Burkhardt et al., 2022).
* Ablations: with/without hourly bins, 2-of-3 vs 1-of-1 and 3-of-4, learning length, floors.
* Uncertainty: none of the outputs carry probe accuracy (EC ±1 % FS = ±200 µS/cm, turbidity ±5 % FS = ±50 NTU, DO ±3 % FS for the
  selected DFRobot probes).
* A sensor-fault layer before event detection: flat-line, spike, rate-of-change, drift-after-wipe checks (Leigh et al., 2019 frame
  technical anomalies separately from events).
* Field validation: co-located grab samples analysed by a lab; logged events vs. known discharges; a false-alarm budget per month.

## 3. Proxy anomaly engine (Mahalanobis) — `train_proxy_anomaly_engine.py`
Six features (pH, turbidity, temperature, EC, DO, depth), mean and covariance from the 2,816 normal rows, covariance regularised by
1e-4 I, distance threshold 4.011 at the 99.5th percentile. A single global Gaussian treats the diurnal cycle as variance, which
widens the normal region. Output header regenerated identically (line endings aside); unused by the firmware.

## 4. Plume transport model — `advection_dispersion_model.py`
* Equation: 1-D slug release in a uniform channel, C = M/(A√(4πDt))·exp(−(x−Ut)²/(4Dt) − kt), M = 500 kg, A = 50 × 1.8 m², U = 0.6 m/s,
  k = 5e-6 s⁻¹. Correct for a cross-sectionally mixed plume.
* Dispersion coefficient ([dispersion_check.py](../audit/verification/dispersion_check.py)): Fischer 70.0 m²/s (correct). The coded
  Kashefipour–Falconer value, 777.9 m²/s, matches neither published form: the paper's equation for W/H ≤ 50 (here 27.8) gives
  97.2 m²/s in the form most often cited, or 428.8 m²/s in the variant printed in a 2021 review table; check the original. The model's
  "uncertainty band" between Fischer and the coded value is therefore too wide, and peak concentrations are ≈ 2.2× too low if (ii) holds.
* Validity: a bank outfall needs ≈ 7 km (a centreline release ≈ 1.8 km) to mix across a 50 m channel, so the 4.5 km receptor is in
  the near field where the 1-D solution is not valid.
* Distances are straight-line (19 km) although the code comment estimates ≈ 22.8 km of channel; arrival times scale with distance.
* Travel time band 0.2–1.0 m/s gives 5.3–26.4 h to Puntamba; the dashboard animates at 0.75 m/s.

## 5. Sampling, timing and calibration
* 15-minute sampling resolves events lasting ≥ 30 minutes; the timer restarts after the wake work, so the real period is longer.
* Temporal dependence: the 2-of-3 rule is a crude filter for autocorrelated noise; real data will contain bursts that defeat it.
* Calibration: pH drift, conductivity cell fouling and optical DO cap ageing (≈ 1 year) need a schedule; USGS TM1-D3 (Wagner et al.,
  2006) defines field cleaning, fouling and drift corrections for exactly these parameters.
* Warm-up: optical DO response ≤ 60 s; firmware waits 1 s.

## 7. Recommended analytics work (in order)
1. Add an event-level evaluation (latency, recall, false alarms per month) to `evaluate.py`, starting from the audit script.
2. Fix the decision state machine: reset risk after learning, one trigger per event, consume `valid[]`, persist baselines in NVS.
3. Build a harder synthetic benchmark (drift, fouling, spikes, dropouts, rain pulses, smaller events) and report sensitivity curves.
4. Compare against simple baselines and CANARY on the same data.
5. Collect a pilot dataset with lab grab samples before claiming detection performance in a real river.
